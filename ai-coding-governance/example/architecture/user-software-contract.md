# ユーザーとの境界を先に設計する

対応する正規ルールは [`../../references/user-software.md`](../../references/user-software.md) です。

## 要件

ユーザーが保存済みのレポートを削除できるようにする。削除は元に戻せない操作なので、実行前に影響を理解でき、失敗した場合はレポートを失わずにやり直せるようにする。

## やらないこと

- ユーザーにデータベースの削除状態や内部 ID を見せない
- 操作の結果を画面に何も表示せず、成功したかどうかをユーザーに推測させない
- 失敗したのに一覧から先に消してしまい、再試行や復旧をできなくしない
- 今回必要のないゴミ箱、復元期間、監査画面を追加しない

## decision diff

- ユーザーが理解する概念: レポートを削除するという操作と、その結果
- ユーザーに見せる状態: 削除前の確認、成功後の一覧、失敗時のエラーと再試行
- 新しい永続化: なし。現在の削除処理を使う
- 承認が必要な判断: 削除を取り消せる要件が必要になった場合は、別の設計判断として扱う

## 普通の実装の全体像

まず画面上で操作の影響を明示し、実行後はサーバーの結果に合わせて表示を更新します。失敗時はレポートを一覧に残し、ユーザーが同じ操作を再試行できます。

```erb
<%= button_to "レポートを削除",
              report_path(report),
              method: :delete,
              data: { turbo_confirm: "このレポートを削除します。元に戻せません。" } %>
```

```ruby
def destroy
  @report = current_user.reports.find(params[:id])
  @report.destroy!
  redirect_to reports_path, notice: "レポートを削除しました。"
rescue ActiveRecord::RecordNotDestroyed
  redirect_to reports_path,
              alert: "レポートを削除できませんでした。内容を確認してもう一度試してください。"
end
```

この例で重要なのは、削除 API を呼ぶことだけではありません。ユーザーの意図、不可逆性、結果、失敗時の復旧方法を一つの体験として設計していることです。

## レビュー観点

- ユーザーが実行前に操作の影響を理解できるか
- 成功、処理中、失敗の状態がユーザーに伝わるか
- 失敗時にデータや入力を不必要に失っていないか
- 内部の status、ID、例外をそのままユーザー向け概念にしていないか
- 取り消しやゴミ箱など、未要求の将来要件を混ぜていないか
